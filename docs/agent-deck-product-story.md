# Agent Deck：让每一次 Agent 对话，都走向一个可验证的结果

> 面向外部发布的产品介绍稿 · 2026 年 9 月

## 一句话介绍

**Agent Deck 是一款 macOS-first、local-first 的智能工作桌面。它把散落的 AI 对话，变成可规划、可并行、可干预、可验收、可复用的真实工作。**

它不是另一个聊天框，也不是简单的多 Agent 看板。Agent Deck 想解决的是一个越来越普遍的问题：当 AI 可以同时推进很多任务时，人怎样保持注意力、上下文和最终决策的控制权？

## 为什么要做 Agent Deck

过去，我们和 AI 的协作大多停留在“发一句话，等一个回答”。这种方式适合单点问题，却很难承载真正复杂的工作：

- 一个需求需要调研、实现、测试、评审和交付，多个环节可以并行，也存在依赖；
- 多个会话同时运行后，人需要不断切换窗口、重复背景、追问状态；
- Agent 说“完成了”，但文件、测试、命令和来源并不一定可验证；
- 上下文越堆越长，Token 越花越多，重要信息反而被噪音淹没；
- 最终只知道“花了多少 Token”，却不知道这次工作有没有真正创造价值。

我们判断，AI 能力继续增强以后，稀缺资源不再只是模型智力，而是人的注意力，以及把智能稳定转化为结果的执行系统。

这就是 Agent Deck 的起点。

## 从一句目标，到一个可验收的交付

Agent Deck 把一次复杂工作组织成一条清晰的闭环：

1. **写下目标**：描述想得到的结果、完成标准、工作区与执行预算。
2. **选择最轻的执行方式**：简单任务直接由一个 Agent 完成；复杂任务才进入主 Agent 规划与多 Agent 协作。
3. **在真实环境中执行**：每个 Worker 使用真实会话和本地工作区；需要隔离时使用 Git Worktree。
4. **只共享必要上下文**：Context Kernel 按任务装配已验证事实、依赖、决策和证据引用，而不是广播所有聊天记录。
5. **把人的注意力放在决定上**：系统告诉你现在最需要处理的一件事、为什么是现在，以及它会释放哪些下游工作。
6. **用证据验收结果**：产物、Diff、测试、命令和来源可以追溯；失败和阻塞也会被如实呈现。
7. **复核执行记录**：区分实际 Token 用量与本地估算，回看交付证据与失败原因。

```text
目标 → 自适应路由 → 真实执行 → 证据审阅 → 交付物 → 记录复核
                    ↑          ↓
              最小上下文    人类决策
```

## 不是“更多 Agent”，而是更少失控

### 1. Session 与 Mission，是两种不同的工作尺度

独立 Session 适合连续、清晰的单人协作：它保留自己的目标、上下文、工作区、终端与运行状态。

Mission 用于真正需要拆解的复杂任务：主 Agent 生成可确认的计划，Worker 根据依赖并行推进，人只在计划、阻塞、结果和集成等关键节点介入。Mission 是关系层，不会把所有会话强行混成一段上下文。

### 2. Adaptive Runtime，让编排成本必须“物有所值”

多 Agent 并不天然更快。对于边界明确、上下文连续的任务，额外的 Planner 和 Worker 反而会带来延迟、Token 和交接损耗。

Agent Deck 因此使用本地、确定性的路由策略：

| 工作类型 | 执行方式 | 目标 |
| --- | --- | --- |
| 边界清晰的修改 | Direct：0 Planner + 1 Worker | 保持一个连续上下文，减少协调开销 |
| 多个相对独立的交付项 | Coordinated Mission | 用依赖图控制并行和验收 |
| 调研、架构、迁移、审计 | Orchestrated Mission | 多源工作并行，保留来源、证据与综合评审 |

系统默认选择足以保证质量的最轻拓扑，用户也可以显式覆盖。

### 3. Context Kernel，让共享上下文紧密但不臃肿

Agent Deck 不把完整聊天复制给每一个 Agent。它围绕当前任务组装“上下文胶囊”：目标、约束、依赖产物、已验证事实、未决问题、风险和可追溯引用。

这让每个 Agent 知道自己该知道的，同时避免多份重复长上下文持续消耗 Token。后续的 Trajectory Index 还会把任务、工具调用、决策和证据连接成可检索轨迹，让历史经验可以按结构和语义被重新找到。

### 4. Attention OS，让不同的人用不同方式掌控工作

注意力没有唯一范式。有人希望一次只处理一个决定，有人习惯看全局，有人只想在开会前读一页简报。

Agent Deck 在同一份真实状态之上提供多种视图：

- **Focus Queue**：只呈现当前最重要的一个决定；
- **Control Room**：跨 Mission 查看阻塞、评审和运行状态；
- **Briefing**：用一页内容总结进展、风险、交付与待决策项；
- **Priority Modes**：按推进、交付、风险或价值密度排序，但不会替用户自动批准工作。

### 5. Evidence-first：完成不是一句状态，而是一组证据

每一个关键结论都应当能够回到原始对话、文件、命令、测试或来源。面向人阅读的报告优先产出自包含 HTML；JSON、CSV、图片、Diff 和命令输出作为原始附件保留。

当任务阻塞时，产品不只显示一个黄色标签，而应告诉用户：真实原因是什么、应该对谁说什么、处理后会释放哪些任务。

### 6. 真实用量与执行证据

记录 Planner 和 Worker 的 Token 用量，明确区分 Provider 实测与本地估算。将产物、测试、来源和运行记录保存在本地，方便复核执行质量与定位问题。不将 Token 消耗换算成财务收益。

## 当前已经可以体验什么

当前版本已经打通了以下真实链路：

- macOS 桌面端与本地工作区；
- 多条真实 Codex 会话的统一管理；
- Direct 与 Mission 两种执行路径；
- 主 Agent 计划、任务 DAG、Worker、依赖和人工审批；
- Git Worktree 隔离、Diff、测试、命令与失败证据；
- Worker 对话、消息回执、运行历史和人工干预；
- Focus Queue、Control Room、Briefing 与显式延后；
- Context Kernel 的预算化上下文装配；
- 自包含 HTML 交付物、附件、预览、导出和本地定位；
- 本地 SQLite 账本，以及 Provider Token 真值的记录基础；
- 可复现的 Agent Deck 与直接 Codex 对照评测工具。

当前以 **Codex-first** 为主链路。Provider 层采用适配器设计，但 Claude Code、Trae 和通用 API Provider 的 Mission 级完整体验仍在建设中，不作为现阶段承诺。

## 我们如何看待性能

Agent Deck 不回避多 Agent 的成本，也不会用“Agent 数量”代替有效产出。

在首轮三个同题、同模型、同推理档位的简单任务配对实验中，双方都通过了全部隐藏检查，Agent Deck Direct 与直接 Codex 的几何平均耗时接近持平。重复实验也观察到了明显方差，因此这只是早期工程证据，不是稳定领先结论。

我们已经把这种对比做成可复现的评测和回归门禁。下一阶段的目标很明确：简单任务不因编排而显著退化，复杂任务则必须在质量、注意力成本或交付完整度上给出可验证收益。

## 适合率先使用 Agent Deck 的场景

| 场景 | 典型工作流 | 希望改善的指标 |
| --- | --- | --- |
| 复杂研发交付 | 需求 → 计划 → 代码 / 测试 / 评审 → 验收 | 周期、返工、人工工时、风险 |
| 有证据的技术调研 | 多源检索 → 数据治理 → 对比 → HTML 报告 | 调研人天、可追溯率、复用次数 |
| 故障排查与修复 | 诊断 → 并行验证 → 修复 → 回归 | MTTR、重复排查、误操作 |
| 发布级内容生产 | 选题 → 核验 → 写作 / 审稿 → 发布草稿 | 周期、审核返工、内容复用 |
| 决策准备与项目推进 | 目标 → 方案 → 风险依赖 → 决策简报 | 等待时间、会议时长、采纳率 |

## 接下来要做什么

我们的近期重点不是继续堆功能，而是把核心闭环做深：

1. 稳定 Direct 路径的速度与质量，并完成简单、中等、复杂任务的重复评测；
2. 建立 Token Budget Governor，在超预算之前自动降噪、降并发或请求确认；
3. 完善运行中的预算控制和失败恢复；
4. 强化轨迹级检索和上下文质量评估；
5. 让 Provider 适配器通过统一能力契约，再逐步扩展 Codex 之外的运行时；
6. 继续收敛桌面体验，让第一次使用的人只需要理解“工作、待我处理、结果”三个核心入口。
