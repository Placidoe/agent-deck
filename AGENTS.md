# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Selected product direction

- Latest product direction (supersedes the older default multi-session landing): keep only three primary destinations — 工作, 待我处理, 成果 — plus Settings at the bottom. Open on the unified work list. Requirements and unlinked Missions are read-only projections in one list, deduplicated by Mission ID; never create duplicate executions to unify navigation. Parallel sessions remain a one-click work view; DAG and activity are drill-down tools. Use visible text labels, explicit return navigation, and one next action instead of a dashboard of competing controls. Preserve all existing records and approval gates.

- The product is a dark, native-feeling macOS control room for managing multiple independent Codex sessions in parallel.
- `Session` is the primary product object. Every session owns its own goal, conversation, context, repository/worktree, terminal, progress, and runtime state.
- The primary surface is a multi-session grid that makes concurrent work immediately visible. A main-agent/subagent topology may exist inside a session, but it is secondary navigation and must not be confused with cross-session management.
- Durable user correction: the desktop product must not present mock orchestration, invented progress, fake latency, fake agents, or synthetic activity as live data. Every operational value must come from a provider event, the local event ledger, Git, or a clearly labelled derived metric. Unsupported capabilities must render as unavailable instead of falling back to mock data.
- The browser build is an honest preview shell only. It may explain that the desktop runtime is required, but must not fabricate sessions, missions, tasks, messages, progress, worktrees, or runtime health.
- Durable user correction: do not frame the product as one mission decomposed into several subagents. Frame it as many Codex conversations running side by side, with optional orchestration inside each conversation.
- Durable user correction: the primary product is an installable PC desktop application, with macOS first. Browser builds are preview/deployment conveniences only; local workspace access must be provided through a secure desktop main-process bridge.
- Durable product direction: support an optional `Mission` orchestration workspace inside the session-first product. A Main Agent produces a structured requirement form and task DAG; Worker Agents expose task state, execution evidence, shared artifacts, and their message-bus communication.
- Durable visual preference: keep the dark macOS control-room aesthetic, but avoid ultra-small 7–9px product text. Task titles and primary controls should generally render around 11–13px, with smaller metadata reserved for secondary evidence.
- Durable workspace UX correction: the active local workspace must be prominently selectable from every session/mission creation dialog. Never present the repository as a disabled text field or hide the only switcher in a status bar; show the resolved absolute path before dispatch.
- Durable mission observability correction: a generated plan is a gated pre-execution state, not success. Label it as awaiting approval, expose the approve action on the graph, and show each task's brief and acceptance criteria before execution plus real provider activity, result text, changed files, and evidence after execution.
- Durable runtime safety correction: Agent Deck must hold a single-instance lock per desktop profile so two app processes cannot recover or mutate the same SQLite mission ledger. SQLite subprocess reads must tolerate mission snapshots beyond Node's default child-process buffer, and persisted provider output must be explicitly bounded while preserving real head/tail evidence.
- Durable performance correction: never send complete Mission snapshots for list or high-frequency provider updates. Use lightweight summaries, selected-Mission detail, cursor-paged event history, coalesced invalidations, a persistent SQLite connection, and lazy-load the graph workspace.
- Durable artifact UX correction: every published file must be visibly clickable, revealable in Finder, and exportable. Resolve symlinks and enforce real-path containment inside the authorized workspace/worktree; missing files must surface a real error. Mission-level reports must be exportable from the evidence ledger.
- Durable Mission inspector correction: selecting the Main Agent or a Worker must open an agent-centered workspace whose default view is the real Codex conversation. Brief, result, and evidence belong in separate tabs; do not stack all of them into one long narrow evidence column or duplicate the Message Bus beneath the graph.
- Durable intervention correction: any persisted Main Agent or Worker thread must expose a fixed, visible composer so the user can send a new turn or steer an active turn. The user's message and the agent's real response must both become visible in the conversation view.
- Durable agent identity correction: Main Agent, Worker roles, and the user should have stable, visually distinct avatars across the Mission sidebar, graph, inspector, and conversation so parallel conversations are easy to distinguish at a glance.
- Durable orchestration truth correction: a Main Agent conversational claim must never be treated as a created subagent. Follow-up delegation must use a structured action contract, atomically register a real Mission task, create its worktree and Codex thread, and surface that persisted Worker on the canvas; otherwise the response is conversation only.
- Durable review UX correction: a Worker in review state must expose a clearly clickable Review entry and a fixed decision bar with “Review result” and “Accept”; users must not need to send a chat message or scroll to the bottom of a long conversation to complete review.
- Durable artifact navigation correction: the selected Main Agent or Worker inspector must expose a first-class `Artifacts` tab with a visible count. Published files must be reachable there with open, Finder reveal, and export actions; do not bury artifacts at the bottom of Evidence.
- Durable layout rule: sidebar controls, scrollable lists, center canvases, and inspectors must occupy explicit grid rows/columns with `min-width: 0`/`min-height: 0`; adding an optional control must not create an implicit grid row. Verify both the default 1540×960 desktop window and the 1120×720 minimum window for overlap, clipping, and horizontal overflow.
- Durable blocked-state UX correction: `Blocked` is a manual-intervention state, never implied background work. Surface the real blocker and preserved state on the graph and selected Worker, provide a concrete suggested instruction, and distinguish continuing the existing thread from redispatching a new Worker.
- Workspace dispatch safety: code development validates Git repository and HEAD before approving or retrying workers. Research/document work is an explicit separate mode: ordinary source folders are reference-only, outputs go into application-owned isolated workspaces whose internal version repository is initialized by the app. Never initialize, import, or commit the user-selected source directory automatically. Allow changing mode or workspace only before any Worker/worktree exists; retain the plan and require explicit renewed approval after a native confirmation. Existing missions default to code mode; never silently downgrade isolation or launch blocked work.
- Durable artifact format preference: human-facing reports, research, plans, reviews, comparisons, and dashboards are HTML-first. Generate self-contained semantic HTML with inline CSS/SVG and embedded machine-readable structured data; keep source code, CSV, JSON, images, and raw evidence in their native formats and use Markdown only when explicitly required. HTML previews must be sandboxed with scripts, network requests, forms, and external embeds disabled.
- Durable dependency-conflict rule: a task without its own provider thread must never fall back to the Main Agent conversation or expose message-based recovery. If dependency branches conflict before dispatch, preserve the isolated merge state, track every dependency branch not yet contained in HEAD, and start a real conflict-resolution Worker in that worktree before continuing the assigned task.
- Durable P0 workflow direction: Mission should present one evidence-backed next human decision at a time. Permission approval, blocked-worker recovery, result review, plan approval, and integration review must be prioritized from persisted state, explain why they matter, and route to the real evidence or conversation without inventing progress or taking action on the user's behalf.
- Durable adaptive-runtime direction: orchestration must earn its overhead. A bounded, coherent code request defaults to one high-quality Worker that keeps implementation and adversarial verification in the same context, skips the Planner/DAG turn, and auto-integrates after one human result review. Research, explicit decomposition, or genuinely independent deliverables use a budget-bounded Mission DAG. Persist and expose the routing decision; keep provider runtimes replaceable behind the same control plane.
- Durable visual correction: prefer calm, native macOS composition over dense control-room chrome. Keep one primary action per region, move secondary Mission views into a compact overflow control, use readable 10–13px body/control text, and avoid decorative cards or high-saturation outlines when they do not communicate state.
- Visual acceptance: Requirements use a quiet split-view inbox with document-like details; Mission decision banners and graph controls occupy normal flow above an independently sized viewport. Never reuse horizontal toolbar styles for document/result headers. Validate real-ledger screenshots at both desktop sizes using the isolated read-only design QA harness before claiming the layout is fixed.
